# ADR-0046 — Business identity: settings stores a file reference, reads `files`, and the logo is retired asynchronously

Date: 2026-10-17. Status: Proposed for Phase 1 row 27h (spec 052). Becomes Accepted when the owner answers BI-Q1…BI-Q4
and the first code PR lands.

## Context

Row 27g needs each business's official name (ar/en) and logo for the attendance statement PDF. ST-Q1 puts both in the
business settings. Image handling belongs to `files` (ADR-0022): content type from bytes, size caps, full re-encode,
R2 keys generated by us, and only `files` may import `packages/storage` (module-map). `settings` imports only `tenancy`
and `identity` today. ADR-0031 already solved "a module stores a file reference" for `staff`.

## Decision

1. **Store on `business_settings`**: `official_name_ar`, `official_name_en`, `logo_file_id`. No new table. A composite FK
   `(company_id, logo_file_id)` to `file_objects` (`ON DELETE RESTRICT`) and a partial unique index per company.
2. **Upload through the unchanged `files` flow** with `owner_module='settings'`, the business as owner entity, stored
   permission `read:settings:business`. Settings binds a **file id** in its own transaction and re-reads the file through
   the existing `files.documentFileFacts` export (extended additively with a `purge_started` flag). This adds one import
   arrow, `settings → files` (read only), declared in `docs/module-map.md` by the first code PR. `files` imports only
   `tenancy`, so there is no cycle. No write crosses modules.
3. **`files` gains two small rules**: `validateStoredPermission` pins `settings` files to `read:settings:business`, and
   `request-upload` applies a per-owner-module size cap (the logo cap, BI-Q3). The generic policy and the DB checks stay.
4. **Replacement and removal** emit `BusinessLogoChanged` through the outbox in the binding transaction. A `files`-owned
   outbox consumer (database only, as ADR-0018 requires) takes the same business lock as binding, then re-checks the current reference through a reverse read port
   (`files → settings`, wired at the composition root, declared in the module map), then sets `purge_started_at`; that commit is the durable
   handoff (a later bind is refused). The existing hourly retention worker then gets a third kind, `retired`, and deletes
   the object outside any DB transaction with the tombstone and a system audit. Storage IO never runs in a request, a
   consumer or a transaction. The consumer ships **before** the producer (27h-3 before 27h-4), so an emitted event always has a registered consumer and is never parked or acknowledged unhandled.
5. **Reading for the statement** is two exports in `settings/index.ts`: `readBusinessIdentity` (ids and names only) and the
   pure `statementIdentity` fallback. The logo **bytes** are read by a `files`-owned export built with 27i, resolving the
   currently bound logo of the authorised statement's business and writing one access-audit row for the requester. The
   statement requester need not hold any settings or files permission, so the stored permission gates only the admin
   preview. The `staff → settings` arrow for 27g is that row's own ADR.

## Consequences

- Two new arrows (read `settings → files`, and the reverse read port `files → settings`, wired at the composition root so
  there is no compile-time cycle) and one new published event; no new dependency, runtime role, grant, or RLS exception.
- The settings read cache must treat entries without the new keys as stale (guard change in `businessSettingsQuery`).
- A READY logo that was uploaded but never bound is an orphan until a later cleanup (deferred issue); a replaced logo
  waits for the retire consumer.
- The settings audit and the event carry ids and names only, never a storage key.
- If settings is extracted later, it needs a files read API for this one check, as with ADR-0031.

## Alternatives rejected

- A separate identity table: a second locked row, audit entity and cache entry for three columns.
- A synchronous `files` retire export called from settings: a cross-module write with storage IO in a transaction.
- Keeping replaced files forever: contradicts the owner decision of 2026-10-03 ("until replacement").
- A cap by content type in the generic upload policy: it would also shrink employee-document images.
- A generic internal "read any file" export for the renderer: bypasses private-document permissions.
