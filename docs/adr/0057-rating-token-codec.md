# ADR-0057 — Rating token codec and key custody

Status: Accepted
Date: 2026-10-30
Amends: ADR-0011 §1

## Context

ADR-0011 stores only SHA-256 of a complete rating token, so a later queued sender cannot recover the original token
from that hash. RT-Q1 resolves this transport gap: Abu Salem's binding answer in batch 40 chooses a keyed,
domain-separated derivation from immutable company/request identity, with the secret held only in Dokploy and the
token produced in sender memory. PP-86.1 places the codec in `packages/auth` behind the separate
`@pospay/auth/rating-token` entry point. PP-86.2 restricts the derivation key to the worker; the API verifies a
presented token by its stored hash and receives no key.

The request id and company id are UUIDv7 values and are therefore guessable. They are context, not secrets. The key
is the only secret in this design.

## Decision

### 1. One deterministic derivation, with separate claim and sender capabilities

`packages/auth/src/rating-token` uses `node:crypto` only and exports a claim codec and a sender codec as separate
objects. Both use exactly this derivation:

```text
enc(parts) = for each part: uint32 big-endian byte length of UTF-8(part) || UTF-8(part)
context    = enc(['pospay:rating-token:derive:v1', String(version), companyId, ratingRequestId])
random     = HMAC-SHA256(keys.get(version), context)            // 32 bytes
token      = companyId + '.' + base64url(random) without padding // 36 + 1 + 43 = 80 chars
tokenHash  = SHA-256(UTF-8(token))                               // 32 bytes
```

The claim side derives with the ring's current version and returns only `tokenHash` and that version. The sender
side derives with the stored `token_key_version`, never falls back to the current version, and returns no token when
that version is absent. The token shape and the stored full-token SHA-256 hash are unchanged from ADR-0011 §1.

The output is pseudorandom because HMAC-SHA256 is a keyed PRF; it is unpredictable only while the key stays secret.
The randomness requirement of ADR-0011 now applies to the derivation key, which is generated by a CSPRNG with at
least 32 bytes. The UUIDv7 ids are guessable, so they provide no secrecy. A leaked key reproduces every unexpired,
unconsumed link exactly.

### 2. Worker-only custody and keyed fingerprints

`RATING_TOKEN_DERIVATION_KEY`, `RATING_TOKEN_DERIVATION_KEY_VERSION` and
`RATING_TOKEN_DERIVATION_RETIRED_KEYS` live only in Dokploy secrets on the worker service. Keys are separate per
environment and are never reused from `STAFF_OTP_*` or `NOTIFICATION_*`. The API receives none of these settings
because it verifies by hash. Configuration keys are copied into owned buffers; the capability log carries a keyed
fingerprint, never key text or a token.

This task wires only that worker capability report. Sub-PR 59b-2 wires the claim codec and 59b-3 wires the sender;
no migration, route, consumer, template or send is enabled here.

### 3. Rotation, retirement and failure behavior

Rotation takes two deploys: first add the new key under retired keys without changing the current version, then
switch the current key and version. A retired key stays in the ring until no `rating_requests` row with
`status = 'SENDING'` and that `token_key_version` remains. A stored version missing from the ring fails closed: no
link is produced and the request stays `SENDING`.

Rotating a key does not revoke links already sent, because verification uses the stored full-token hash rather than
the derivation key. Consequently retirement controls future derivation only; it is not a revocation mechanism for
links already delivered.

## Consequences

- Identical company/request identity and key version produce the same canonical token, so the hash-only customer
  record and the sender agree without storing or transporting plaintext in Postgres, outbox or job payloads.
- Key confidentiality is the entire unpredictability boundary. Disclosure permits exact reproduction of every
  unexpired, unconsumed link; rotating afterward does not invalidate links already sent.
- The API remains key-free and keeps its existing tenant-local hash verification and RLS behavior.
- Operations must retain every version still referenced by a `SENDING` request. Premature retirement stops that
  send without emitting a link and leaves the request available for a later corrected deployment.
- The worker currently reports `RATING_TOKENS` readiness only. Rating claim and delivery remain disabled until
  59b-2 and 59b-3 respectively wire those paths and their own activation gates are satisfied.
