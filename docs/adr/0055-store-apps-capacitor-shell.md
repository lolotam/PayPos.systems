# ADR-0055 — Store apps: a Capacitor shell around `apps/pos` for «PosPay Business»

Status: Proposed (track MOB, sub-PR M-0; number provisional, renumbered at merge).
Date: 2026-10-23. Scope: roadmap track `MOB` (MOB-14 … MOB-19), first deliverable «PosPay Business». Owner decision it
rests on: APP-Q1 (`docs/owner-decisions.ar.md` §22, PP-38.1, batch 54) — two store apps, **final**: Waleed and Abu Salem
both picked option 1 on 2026-10-23. That record is added by PR #532, **which merges before this ADR**. Owner questions
this ADR opened: APP-Q2 … APP-Q7 (`docs/specs/065-mob-app-shell/owner-questions.ar.md`, batch 55, PP-39.1 … PP-39.6),
**answered by both owners on 2026-10-23** (option 1 ⭐ on all six; on APP-Q2 Waleed then moved to option 2 with the
Arabic name «بوس باي للأعمال»; Abu Salem's option 1 binds, and the Arabic name waits for his confirmation). Still open: the legal name of the company, which
is still being formed (APP-Q3, `TODO(spec)`), and **APP-Q8** (how the iOS build is tested without a Mac, and at what
cost; PENDING).

## Context

APP-Q1 replaces "PWA only until Phase 6" with real App Store and Google Play apps:

- **«PosPay Business»**, now: the owner and every employee by permission, plus a cashier mode on tablets and phones that
  works offline (MOB-14, MOB-15, MOB-18).
- **«PosPay»** for customers, later (MOB-16).
- iOS and Android move together, on one codebase each. The full back-office stays web (`apps/admin`).

What exists today and constrains the choice:

1. `apps/pos` is the Vite React PWA (`CLAUDE.md` §2.1): device pairing, staff and personal sessions, attendance, the
   employee's personal screens, local-first storage in IndexedDB through Dexie, a Workbox service worker generated by
   `vite-plugin-pwa`. The cashier screens are still to come in it.
2. `CLAUDE.md` §7 and §11: totals in the POS are computed **by importing `packages/domain`**, the same functions the API
   uses; re-implementing pricing outside it "is a money bug". Any app that sells must run that TypeScript.
3. Authentication transports, as built: the **paired device** sends `Authorization: Device <token>` from IndexedDB
   (`apps/pos/src/shared/api/client.ts`), so it does not depend on the page's origin. The **staff** and **personal**
   sessions (ADR-0019, ADR-0027) are host-only `HttpOnly; Secure; SameSite=Lax; Path=/v1` cookies set by the API host
   and sent by `fetch(…, { credentials: 'include' })`. They work today because `pos.<env>.pospay.systems` and
   `api.<env>.pospay.systems` are the **same site**. Better Auth also checks the request origin against
   `AUTH_TRUSTED_ORIGINS`. Passkeys (ADR-0027, ADR-0039) use the relying party `pospay.systems` (`staging.pospay.systems`
   on staging), and `packages/auth/src/passkey-policy.ts` accepts only the origins `https://app.<rp>` and
   `https://pos.<rp>`, whatever the environment lists.
4. Staff Web Push (ADR-0052) is built on the browser Push API and its service worker. Neither iOS `WKWebView` nor the
   Android WebView exposes the Push API to a page, so inside a store app it does not deliver; native push is MOB-19
   (Waleed, 2026-10-23: 28b-2 stays on Web Push, native push comes later on the same subscriptions table).
5. One developer plus AI implementers (`CLAUDE.md` §0; MiniMax writes production code, PP-10.1). A second UI codebase
   in another language doubles every screen, every test and every review.

## Decision

### 1. Stack: Capacitor around the existing `apps/pos` build

«PosPay Business» is a **Capacitor** app whose web layer is the production build of `apps/pos`. The screens, the Dexie
offline store, the outbox queue, the device pairing and every import of `packages/domain` are the same code the PWA runs.
Native capabilities (push, the printer and the card terminal of MOB-18, secure storage, biometrics) come in as Capacitor
plugins called from `apps/pos` behind small ports, so the web build keeps working without them.

The Capacitor packages (`@capacitor/core`, `@capacitor/cli`, `@capacitor/ios`, `@capacitor/android`) are added at **one
exact version, pinned in sub-PR M-1a**, which states the version it checked against the Xcode and Android Gradle
Plugin versions of the CI images. This ADR does not claim a version verified (the stance ADR-0018 and ADR-0052 took).

Compared:

| Option | Reuses `apps/pos` and `packages/domain` | Offline cashier | Cost for this team | Verdict |
| --- | --- | --- | --- | --- |
| **Capacitor** (web build in a native WebView) | Yes, the same bundle | Yes: Dexie and the bundled assets work with no network | One codebase; native projects are thin | **Chosen** for «PosPay Business» |
| React Native + Expo | `packages/domain` yes (it is pure TypeScript); screens no — every screen rewritten with native components | Yes, with a new storage layer replacing Dexie | Second UI codebase now; strongest native feel; Expo's push and build service | Rejected now; **the candidate for the customer app** (§7) |
| Flutter | No: Dart cannot import `packages/domain`, so pricing would be re-implemented | Yes | Second language and codebase | **Rejected**: breaks `CLAUDE.md` §7 / §11 |
| Native Swift + Kotlin | No, twice | Yes | Two codebases plus the web one | Rejected: three implementations of every screen |
| Stay PWA only | Yes | Yes | None | Rejected by APP-Q1 |

Why the WebView is acceptable here: the business app is forms, lists and a cashier grid, the same screens the PWA
already ships; its weak spot (animation-heavy consumer UI) is exactly the customer app, which this ADR leaves free to
choose React Native. The App Store's minimum-functionality rule is met by an app that ships its own assets, works
offline and uses native push and devices, which is what this ADR builds; a shell that only loads a remote website is
what that rule refuses (decision 3).

### 2. Where the shell lives: `apps/business`

A new workspace app, **`apps/business`**, holds only the native wrapper:

```
apps/business/
  capacitor.config.ts   app id, name, webDir = ../pos/dist-native, server.hostname, plugin config
  ios/                  Xcode project (generated by `cap add ios`, then committed)
  android/              Gradle project (generated by `cap add android`, then committed)
  package.json          @pospay/business — scripts: sync, build:ios, build:android; depends on @pospay/pos
```

- **No TypeScript business code lives in `apps/business`.** Screens, state and native-plugin ports stay in `apps/pos`
  (frontend folders by business, `CLAUDE.md` §7), so the PWA and the app cannot drift. `apps/pos` gains a second Vite
  build mode, `native`, whose output (`dist-native`) skips the service-worker registration (service workers do not run
  on the app's custom scheme and are not needed: the assets are inside the app) and sets a build flag the ports read.
- **The native build needs its own start screen.** The PWA reaches the employee's personal screens only at the path
  `/personal` (`apps/pos/src/app/app.tsx`), and a store app always cold-starts at `/`, which today is device pairing. The
  native mode therefore opens on a choice between «this counter device» (pairing, cashier) and «my employee account»
  (personal OTP), remembered on the phone; the slice spec defines it and M-1a builds it.
- Why not `apps/pos/ios` and `apps/pos/android`: the native projects would enter `apps/pos`'s Docker build context,
  ESLint, Prettier, `max-lines` and Vite watch, and every web change would rebuild them. A separate app keeps the web
  image and the web gates untouched. `^build` would only run the PWA build (outputs `dist/**`), so `turbo.json` gets an
  explicit `@pospay/pos#build:native` task with outputs `dist-native/**`, and the `apps/business` sync task depends on it
  by name; a cache hit then restores `dist-native` instead of leaving it stale or missing.
- `CLAUDE.md` §2.1 gains the line for `apps/business` (and later `apps/customer`) in M-1a; `docs/module-map.md` is not
  affected (it maps backend modules). `.dockerignore`, `.prettierignore` and the ESLint ignores exclude
  `apps/business/{ios,android}`; no Dockerfile copies `apps/business`.

### 3. Bundled assets, and the WebView origin

The app **ships the built assets inside the binary** (Capacitor's default). `server.url` (loading the live
`pos.pospay.systems` site into the WebView) is **refused**: it fails offline on a cold start, it is a remote-website
wrapper in the App Store's eyes, and it would let a server change alter a reviewed binary.

Bundled assets change the page origin, and that is the main technical risk of this ADR (context item 3):

- **Android** can serve the bundle as `https://<pos host>` (`server.androidScheme: 'https'`, `server.hostname`), the same
  origin as the PWA, so the existing cookies, `AUTH_TRUSTED_ORIGINS` and the passkey relying party should keep working,
  and the page stays a secure context.
- **iOS** cannot: `WKWebView` reserves `http` and `https`, so the origin is `capacitor://<host>`. A custom host would
  not make the API's `SameSite=Lax` cookies same-site anyway (the scheme differs), and Capacitor recommends keeping
  `localhost` on iOS because secure-context APIs such as `MediaDevices.getUserMedia`, which the attendance QR scanner
  uses (`apps/pos/src/personal-staff/api/use-attendance-camera.ts`), may otherwise be unavailable. So iOS keeps the
  default origin **`capacitor://localhost`**. Whether WebKit sends a cookie of `https://api.pospay.systems` to a `fetch`
  from that origin is **not verified** and is presumed not to.
- **Decision:** Android sets `server.hostname` to the environment's POS host with the `https` scheme; iOS keeps
  `capacitor://localhost`. **Sub-PR M-1c is a spike against staging** that checks (a) device pairing, (b) a staff PIN
  session and (c) a personal OTP session open and survive a restart, (d) the attendance QR camera opens and reads a
  code, and (e) what passkey attendance does. There is **no Mac** (Waleed, 2026-10-23), and a real iPhone can only get a
  build through a Mac or a paid Apple account. **How iOS is tested, and what it may cost, is owner question APP-Q8
  (PENDING); no money is spent without Waleed's yes.** Its recommended answer gives the spike two steps:
  - **M-1c, no fee:** Android (a)–(e) on a real phone with a side-loaded debug build; iOS (a)–(c) as an automated UI
    test on the iOS simulator of the GitHub macOS runner. The simulator runs the iOS WebKit, so it answers the cookie
    question; it has no camera and no real passkey, so (d) and (e) stay open on iOS.
  - **M-1c-ii, the first real iPhone:** the first TestFlight build of M-2a, installed by the owners only (internal
    testers), repeats (a)–(c) and adds (d) and (e) on iOS.
  **M-1d onward waits for M-1c; the Apple fee waits for M-1c's iOS (a)–(c) to pass on the simulator** (and for the
  company, APP-Q3). **No employee receives the iOS app, and attendance stays hidden on iOS, until M-1c-ii passes.** If (d) fails, the scanner moves to a native camera plugin behind the M-1d port before attendance
  is enabled in the app. If iOS fails (c) or (b), the fallback, in this order, is:
  1. Capacitor's native HTTP and cookie plugins (`CapacitorHttp`, `CapacitorCookies`) with the API hosts listed in
     `WKAppBoundDomains`, so session requests leave through the native stack with the native cookie store;
  2. only if that fails, a native-only session transport (the session token held in the iOS Keychain / Android
     Keystore and sent as a header). That changes `packages/auth` and the security model of ADR-0019 and ADR-0027, so it
     needs **its own ADR addendum and the web manager's agreement**; this track does not change `packages/auth` alone.
- **Passkeys in the WebView** (attendance, ADR-0027 / ADR-0039) are a named open risk, not solved here. On iOS the
  `capacitor://` origin is refused by design by `passkey-policy.ts`; accepting it is a `packages/auth` change that needs
  an ADR-0027 addendum (issue #536), which lands before any native passkey work. On both platforms the app must also be associated with the relying party (Apple
  `webcredentials:` associated domain with an `apple-app-site-association` file; Android Digital Asset Links
  `assetlinks.json`), served from the relying party's host (`pospay.systems`, or `staging.pospay.systems` for the staging
  flavour). Serving those files is an operations change (`deploy/pos-nginx.conf` and Dokploy), made by the web manager or
  Waleed; until it is green, the app hides passkey attendance and the employee clocks in through the PWA or the
  paired-device path.
- Any change to `AUTH_TRUSTED_ORIGINS`, CORS origins or another environment value on staging is a Dokploy change owned
  by the web manager (and production by Waleed). The M-1 plan lists it as an operations step, never as code here.

### 4. Identifiers and the two flavours

The API origin is baked into the build (`VITE_API_URL`, as the staging images do), so there are **two flavours**, each
its own installable app that can sit next to the other on one phone:

| Flavour | Bundle id / application id (APP-Q6, decided) | Talks to | Distribution |
| --- | --- | --- | --- |
| staging | `systems.pospay.business.staging` | `api.staging.pospay.systems` | TestFlight internal + Play internal testing, after every merge |
| production | `systems.pospay.business` | `api.pospay.systems` | TestFlight + Play internal first; store release only on Waleed's typed yes |

The ids are reverse-DNS of the domain we own (ADR-0001); they **cannot be changed after the first upload**, which is
why the owners chose them (APP-Q6). `systems.pospay.app` is reserved for the customer app. The display name is
«PosPay Business» in every language (APP-Q2: Abu Salem's option 1, which binds). An Arabic name «بوس باي للأعمال» on
phones set to Arabic is Waleed's later pick and Abu Salem's note points the same way, but it is `TODO(spec)` until Abu
Salem confirms it. Version: `apps/business/package.json` `version` (user-visible, semver); build number: the CI run number
(monotonic, as both stores require).

### 5. Signing keys live in CI secrets only

- No key, certificate, profile, keystore or store credential is ever committed, written into a Docker image, logged or
  pasted into a document (`CLAUDE.md` §8). The repository holds only the variable names, listed in
  `apps/business/README.md` with empty values.
- They are **GitHub Actions secrets of the environment `mobile-release`**, whose **deployment-branch policy allows
  `main` only**, so a workflow on another branch, a `workflow_dispatch` run on a feature branch or a pull request that
  edits `mobile.yml` cannot receive them; pull-request jobs never see them. Internal builds after a merge need no manual
  approval. A required reviewer (Waleed) guards a second environment, `store-release`, used only by the public-release
  lane (MOB-17). Both settings are confirmed in the GitHub environment settings by the sub-PR that writes stage C.
- iOS: an App Store Connect API key (key id, issuer id, `.p8`), the distribution certificate (`.p12` and its password)
  and the provisioning profiles, both flavours. Android: the **upload** key (keystore, its password, alias) and a Google
  Play service-account JSON limited to the two apps. Google Play App Signing keeps the app-signing key at Google, so a
  leaked upload key is replaceable rather than fatal.
- The keys are created by the account holder (Abu Salem, APP-Q3) on their own machine and entered into GitHub by them or by Waleed.
  No agent creates, reads or stores them; the agent only names the secret each job expects.

### 6. CI builds and distribution after every merge

A **separate workflow** `.github/workflows/mobile.yml`, so `ci.yml` and its required `ci-gate` are untouched. It
copies `ci.yml`'s pattern rather than a workflow-level `paths` filter: it always runs, a first `changes` job decides
whether the app's inputs changed, the build jobs run only then, and an always-present `mobile-gate` job reports the
result (a path-filtered workflow never reports, so it could never become a required check). The app's inputs are
`apps/pos/**`, `apps/business/**`, `packages/**`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, the root `package.json`,
`turbo.json`, `.nvmrc` and `mobile.yml` itself.

| Stage | When | Runner | Needs accounts | Output |
| --- | --- | --- | --- | --- |
| A. Android debug + unsigned AAB | PR and `main`, when the app's inputs change | `ubuntu-latest` | No | AAB/APK as a workflow artifact |
| B. iOS simulator build, no signing | same trigger | `macos-latest` | No | `.app` for the simulator as an artifact |
| C. Signed release builds + upload | `push` to `main` only, environment `mobile-release` | Ubuntu (Android), macOS (iOS) | Yes (company accounts, APP-Q3 / APP-Q4) | TestFlight internal and Play internal testing, both flavours |

- Stages A and B arrive with M-1 and cost nothing in store fees. **Stage C is written only after the company that will
  own the store accounts is formed and its accounts exist** (APP-Q3: the accounts are in the company's name, the company
  is still being formed, and Abu Salem is the account holder; APP-Q4: its D-U-N-S number is requested after that). Until
  then nothing is uploaded and no account is paid for.
- The upload tool is **fastlane** (`pilot` for TestFlight, `supply` for Play) at a version pinned in a committed
  `Gemfile.lock`, added in the sub-PR that writes stage C; it is the standard path for both stores and keeps third-party
  GitHub Actions out of the release path (the stance `ci.yml` takes for images). The sub-PR names the version it checked.
- Before the first stage-C upload, both stores need their app records: an App Store Connect app record per flavour, and
  per flavour a Play Console app with one build uploaded by hand (Play's API refuses uploads to an app with none). The
  account holder creates them (plan step O-2b); no automation creates store records.
- **Cost:** a macOS runner minute is billed at about ten Linux minutes on a private repository. Stage B therefore runs
  only when the app's inputs change, and if the minutes become a problem it moves to `main` pushes plus a manual
  dispatch; the PR body of M-1b reports the measured minutes.
- `mobile-gate` starts advisory (not required by branch protection; `ci.yml`'s required `ci-gate` is unchanged); it
  becomes required only when the web manager and Waleed agree, after it has been stable on `main` for a week.
- **"After every merge"** means every merge to `main` that changes the app's inputs produces a new internal build of
  the **staging flavour** only (it talks to staging, which is redeployed after every merge). The **production flavour**
  is built and uploaded only from a commit that has been deployed to the production API, in the same release that Waleed
  approves with his typed yes, so a production build never calls routes production does not serve yet. A public store
  release is never automatic either.

### 7. The customer app is decided later

«PosPay» for customers (MOB-16) gets its own ADR when it starts. **React Native + Expo** is the recorded candidate: a
consumer app benefits from native components, it does not share the staff screens, and it can still import
`packages/domain` and `packages/contracts`. Capacitor stays possible if the customer app turns out to be a thin
ordering and booking flow. It would live in `apps/customer`.

Abu Salem's note on APP-Q1 (2026-10-23) sets its scope: a customer sees their bookings, purchases, points, packages
(and what is left in them) and refunds **across every business on the platform**, not only one salon. That is a view
across tenants, which RLS forbids by design (`CLAUDE.md` §5: every tenant query runs inside one `withTenant()`). It needs
**its own ADR before any customer-app work**: the customer's global identity, how a customer is linked to each
company's customer record, and the read path that gathers per-company data without a cross-tenant query. This ADR does
not decide it.

### 8. Native push is MOB-19, on `push_subscriptions`

Native push (APNs, FCM) reuses the `push_subscriptions` table and the `PUSH` recipient kind of ADR-0052, so producers do
not change. Three things this ADR records as **pointers only** for MOB-19's own ADR:

- the table needs a transport kind (`WEB_PUSH`, `APNS`, `FCM`) added by expand/contract, with a device token in place of
  endpoint and keys for the native kinds;
- ADR-0052's `isAllowedPushEndpoint` allowlist and request-forgery guard are Web Push only; a native token is not a URL
  and needs its own validation;
- unlike the VAPID key, an APNs key or an FCM service account is a third-party credential: `CLAUDE.md` §8 envelope
  encryption and worker-only custody apply.

Until MOB-19 ships, the app hides the Web Push control on native (the Push API is absent there) and employees who want
notices keep the PWA installed for them.

## Consequences

- One codebase serves the PWA and both store apps; pricing stays in `packages/domain` (`CLAUDE.md` §7 holds).
- A new framework enters the repo (Capacitor, and fastlane for stage C); this ADR is the record `CLAUDE.md` §11 asks for.
  `docs/06_Tech_Stack_Architecture_EN.md` (V1.3) has no mobile section; the web manager adds one after this ADR is
  accepted. This PR does not edit `06`, `CLAUDE.md`, `ci.yml` or `docs/owner-decisions.ar.md`.
- **Installed apps lag behind the server.** Unlike the PWA, a store app keeps running an old bundle until the user
  updates. The API must stay compatible with the oldest supported app version, and the app needs a minimum-version check
  (sub-PR M-1f), which must be inside **the first signed build** (M-2a depends on it): a binary without the check can
  never be told to update. The minimum version is not a new API route (`CLAUDE.md` §6 allows no unguarded endpoint): it
  is a static file served by the POS host and changed by a deploy; M-1f's spec fixes its path and shape. Over-the-air web updates (a hosted live-update service) are out of scope: a new vendor needs its own ADR.
- Every merge that touches `apps/pos` costs CI minutes on macOS if APP-Q8 keeps the macOS runner; measured in M-1b.
- The auth-transport risk on iOS (decision 3) is the gate of the whole track: if neither cookie path works, the track
  stops at M-1c and the session-transport question goes back to the owners and the web manager.
- Passkey attendance and native push are not available in the first internal builds; the PWA covers both meanwhile.
- No store fee is paid and no account is created by this ADR. Apple's developer programme is a yearly fee and Google
  Play's a one-time fee; both wait for the company to be formed (APP-Q3).
