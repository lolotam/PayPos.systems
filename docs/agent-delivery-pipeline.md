- **Automatic switch (PP-112).** A role moves to the next lane of its chain at once, without asking, after the current lane failed **twice** on availability: the server does not answer, the quota or rate limit is exhausted, or the sign-in fails. A poor delivery is not an availability failure: it stays under §§6–8. Before switching, confirm the failed attempt is finished or cancel it (`task_cancel`), so two lanes never write to the same worktree. The task report and the PR description name the switch (which lane failed, how, and which lane took over). The **next task starts on the primary again**; a switch never carries over to another task. The chains in the table replace the earlier "stop and ask Waleed" on a non-quota failure and the earlier "hold until the quota renews": both now move to the next lane. Only when every lane of a chain has failed twice does the dispatch stop and report to Waleed. ## 1. Orchestrator: refresh the real state, then choose the task

- Refresh first: the repository working tree and recent history, the roadmap on https://plan.pospay.systems, the live decisions and the reviews of **both** Waleed and Abu Salem, and every open partner request.
- One use case per PR (`CLAUDE.md` §1). A task needing two use cases is two PRs.
- Each task runs on its own branch and in its own worktree, so unrelated local work in the main checkout is preserved untouched and never swept into a diff.
- Never treat a task as ready because it looks ready: verify it against the live page and the repository.

### 1.1 Management session, task sessions and worktree lifecycle

- Keep a persistent **project-management session** for priorities, milestones, decisions, provider usage and coordination. Keep its status tied to repository, task and review evidence.
- Give each **independent delivery ending in a PR** its own task session, branch and worktree. The unit is a deliverable, not each implementation, test or correction step. Existing in-progress work stays attached to its current task and worktree.
- Keep implementation, related tests and corrections attached to that same task. Delegated stages still follow §§0 and 5–8; a new session or worktree never resets the task's logical correction budget or changes implementer ownership.
- Give the reviewer fresh, independent context. A read-only reviewer may inspect the task's existing worktree; a separate checkout is needed only when the assigned work requires one. Preserve the declared write scopes and concurrency limit in §13.
- A new session needs a short, current handoff: task and approved scope, branch/worktree and HEAD, decisions, completed work, actual check/review receipts, remaining work, blockers, correction-budget usage and any live worker or process it must account for. Do not assume session history transfers automatically; do not include secrets.
- **Closing a session is distinct from stopping its workers or processes and from removing its worktree.** Before closing it, account for delegated work, tests, owned database containers and any other live process; finish, transfer or explicitly stop that work rather than leaving its ownership unclear.
- Remove a task worktree only after its PR is merged and delivery verification is complete, with important work and audit evidence preserved. Check tracked changes, untracked files and valuable ignored files; `git status` alone is insufficient. Account for live workers, processes and owned containers before removal. Never force removal past these checks or sweep another task's files into cleanup.
- This policy does not itself create or close sessions, remove existing worktrees or schedule automatic cleanup. Dependent tasks and the existing review, backup and staging gates remain governed by §§8–10 and 13.

## 2. Every new task starts with the grilling round

- Use the installed **`grill-me`** skill (its underlying **`grilling`** skill) before **every new task**. Discover it by name in the runtime skill catalog; if the catalog does not list it, locate and read the installed `SKILL.md` (a stable hint is `~/.agents/skills/grill-me/SKILL.md`). Do not hardcode a synced-folder hash here, and do not guess a path.
- If neither the catalog nor the installed files can be found, say so plainly and ask the owner. **Never silently substitute another interview skill** (for example `interview-me`).
- The order is fixed:
  1. Inspect the discoverable facts yourself. Never ask the owner for something the repository, the spec, the roadmap or the decisions page already answers.
  2. Map the unresolved decision frontier for this task — what is genuinely undecided.
  3. Ask every independent, ready question in **numbered rounds**, each question carrying a recommended answer.
  4. Wait for the answers and the confirmation before any implementation starts.
- Do not re-ask a question the decisions page has already settled, and do not reopen a settled answer unless the owner asks for it.
- The spec, the plan and the questions of this round are drafted on the **planner lane** of §0 (`claude-opus-5-5`, effort `high`). That lane writes documentation only; it does not write application code.

## 6. The orchestrator reviews and runs the gates itself

- The orchestrator reads the delivered changes personally and runs the gates itself. A worker's claim that a check passed is never a result.
- **The heavy suites run in CI only** (PP-113.1, PP-69.7). **Locally**, only the typecheck, lint, `pnpm lint:docs`, boundaries, `pnpm module-map:check` and the slice's own tests (excluding the Playwright E2E or any other CI-only heavy gate, SA-15 rule 5) run. The component coverage of `pnpm check`, the full API suite (4 shards on CI) and every other required suite are decided by **CI: the `ci-gate` result reported on the exact head being merged** (on a pull request, some jobs check out GitHub's merge ref for that head). **That result counts only when the base parent of the merge commit CI tested equals the current `main`** (comparing start times is not enough: an infrastructure rerun keeps the original merge SHA). Jobs that check out the merge ref (`check`, `api-tests`, build and images) test the head merged with `main` as of that run, and branch protection on `main` does not require the branch to be up to date. Before the PP-72.2 workflow lands, the existing `full-check` head-check job remains required as well; afterward it no longer exists, and its former command coverage is provided by the retained jobs, including both API-client checks in `check`. Never require or read a removed job's result. When the two differ, the branch is updated and CI runs newly triggered by a new push, not rerun, before «دورك» and the merge (§10). No session waits for a free machine "slot" before a check.
- The gates, as the slice requires them: all components of `pnpm check` on CI (distributed under PP-72.2 after its workflow lands; current full-check remains required until then); typecheck; lint; `pnpm lint:docs`; boundaries; cycles; `pnpm module-map:check`; unit; integration; RLS negative tests; `EXPLAIN` checks; the regenerated OpenAPI and the generated clients; and the relevant UI, E2E, build and Docker CI steps. Beyond the local set above, CI runs them. The exception is a gate CI does not run yet (today the Playwright E2E, which no CI job invokes). The super admin's SA-15 rule 5 (not PP-113) says: «If a gate is not in CI yet, add it to the workflow as part of the task. Do not move it back to the local machine.» A new job is a gate only when it is also listed in `ci-gate`'s `needs` and checked by its result script; the slice that needs it does that in its own task.
- Integration and RLS tests run against a **real Postgres** of ADR-0006 (the compose stack, one cloned database per spec file): the full suites on CI, and locally only the slice's own database specs. Each worktree gets **its own local Postgres container** on its own port, so parallel PRs migrate and test separate databases at the same time (PP-69.9). **Never** run tests against a shared or staging database.
- **A failure that repeats in CI is real, not load** (PP-113). The session stops and triages it from the CI log. It never reruns before the failure is diagnosed and a relevant fix is pushed; one rerun is allowed only for a clearly infrastructural failure (a runner died, a network timeout), with the reason written down (SA-15 rule 4). A **draft PR** may be opened only to get a CI run, with no review requests: it gets no `@codex review` and no other review trigger until it is marked ready for review (the exemption to §9's rule below).
- The guards run as well: `clean-code-guard` on production code, `test-guard` on tests, `docs-guard` on documentation.
- A gate counts as passed **only** when that exact command ran and returned success. Record every failure, stale artifact and limitation instead of rounding it up to "passed".
- Every change the implementer made is read **before** it is executed. No script, test, config or package change is executed unreviewed.

## 7. Handoff: when the work moves from one implementer to another

- The **initial implementer keeps its own failed attempt** until the required checks and the review are complete and ownership is handed back. A tool that resumes the original worker cannot move failed work to another model to get past a failure, and a failing delivery is never marked complete to force a handoff. This governs a failure of the work itself. **An availability switch is the one exception (PP-112):** when the implementer's lane fails twice on availability (§0), the next lane of its chain takes the task over, briefed on what is done and what is left, and the report and the PR description name the switch.
- Only after a **clean initial handoff** does a **new, bounded Kimi `K3.1 Pro` task** take the subsequent review, PR and CI findings (down the correction chain of §0 — Kimi CLI lane, MiniMax, Claude Sonnet — when Kimi is unavailable, PP-112; the Kimi CLI lane is skipped on a clear Kimi quota error, PP-113.2). ## 9. Pull request and CI

Do not push one finding at a time. A missing or failed review does not complete the round. Retrigger the required reviews on the new head and keep the existing five-round cap. - Approval means: **all five required reviews are complete on the exact head being merged**, every finding they raised is fixed or properly deferred under the §8 severity policy, **no P0 or P1 is open**, and CI is green **on that same head**. A pending, missing, failed or stale receipt is not a completed review. A neutral or comment-style review counts as complete: the requirement is that all five answered and their findings are resolved, not that all five explicitly approve.

## 10. Merge and staging

- **Ordinary PR ownership (PP-117).** The PR's session may merge without another manager or Super Admin approval after all exact-head checks/reviews, resolved findings, verified applicable backup and its verified restore, and coordinated order pass. A migration PR is merged by the manager after the same gates and the coordinated migration order pass (PP-124); deploy changes (including release controls outside `deploy/`), production and production-data changes, server changes, secret changes and HOLD cases go directly to Waleed. This does not waive any quality gate.
- **Batch staging (PP-114.6).** DEP-1 is the existing staging release session linked below. It releases a completed batch daily or after 3–5 eligible merges, whichever comes first, with the same release gates. A docs-only PR needs no application rollout. [DEP-1](<t3-thread://v2/438824e0-fe19-4a22-bb31-f81eff7b7322/mcp:launch:beb374ef5917d8d28e8ae280ec01994f30e25ad32cea802bdfa8c8ffbb707bd0>) remains the release lane; no alternative path is authorized.

- The owner has generally authorized **reviewed PR → merge → staging, for the delivery queue only**. A change outside that queue — this file's own save, for example — is not published without a fresh instruction.
- **CI must be fresh at the merge (PP-113).** The merge needs the `ci-gate` run on the exact head, and that run counts only when the base parent of the merge commit CI tested equals the current `main`: the merge-ref jobs test the head merged with `main` as of that run, `main` does not require the branch to be up to date, and a permitted infrastructure rerun keeps the original merge SHA, so a start-time comparison could accept a stale result. A rebase or branch update makes a new head: §9 applies to it in full, and the per-merge rebases of §13 (PP-111.2) keep applying unchanged.
- **A merge to `main` is not by itself a release.** The owner recorded on 2026-10-28 that a merge to `main` auto-deploys through Dokploy (PP-69.11); that stays the owner's policy. What PR #701 actually proved is narrower: the live staging service is an existing Dokploy **raw compose** whose image references are **pinned to a SHA**, and that release needed an explicit update of the persistent compose definition plus a controlled deploy through the official Dokploy API. A merge, or an `autoDeploy` flag, is **not proof of a release**. Before claiming a release, inspect what actually happened: the CI run on the merged SHA, the built images, the pinned refs in the live compose definition and the live SHA. The general authorization above covers the reviewed merge and the rollout it may trigger.
- Dokploy takes no backup before a deploy. - **Staging fallback (PP-112):** the deploy runs through the Dokploy connector. - A **documentation-only** change needs **no application rollout**. For the two documentation paths changed in PP-73, the pull request is classified as non-code: every heavy job retained in the applicable workflow must be skipped and `ci-gate` requires exactly that: currently `check`, `full-check`, `api-tests`, `build`, `images`; after PP-72.2, `check`, `api-tests`, `build`, `images`, with no `full-check` result reference (`.github/workflows/ci.yml`). - No production change, no server change, no new credential and no new cost without a specific owner consent.

## 14. Stuck sessions, background waits and delivery size (PP-112)

- **Stuck-session check every 30 minutes.** The manager (or its scheduled watcher) checks every open task session every 30 minutes. A session that is neither working nor waiting on a recorded event (a delegate, a background command, a review, an owner answer) is stuck: the manager nudges it, or moves its work under §0 and §1.1, and the next report names it.
- **Wait on background work so it wakes the session.** A session that starts a background command or Monitor it depends on (tests, a build) calls `t3_background_wait` with that task's id before ending its turn, so the result wakes it. A running delegate is followed through its `next`, never polled with sleeps, loops or repeated status calls. Waiting without a wake-up is not allowed.
- **Delivery size.** Every implementer brief states the expected size of the change. A delivery more than **twice** that size is refused.
