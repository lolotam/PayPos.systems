## What changes for a user

Today the chosen style lives in a cookie on one device and every sign-in resets it to C. After this slice the choice is saved on the user's account: picking a style saves it, and signing in on any browser starts on the saved style from the first screen. A user who never chose still starts on C. If the save fails the frame still changes and a message says the choice was not saved to the account. If the account cannot be read at sign-in, sign-in is not held up and the user starts on C.

## In scope

### 1. Contract (`packages/contracts`)

`src/identity/me-preferences.ts`: `navStyle` enum `'A' | 'B' | 'C'`; `myPreferencesResponse = { navStyle: navStyle | null }`; `setMyPreferencesInput = { navStyle: navStyle | null }` (the key is required; `null` returns to the default). Strict object: unknown keys are refused. Exported from the package index **and registered for OpenAPI** the way the other `me` routes are (`src/identity/me-openapi.ts`, `openapi-schemas.ts`); an index export alone does not put the routes in the document. The OpenAPI document and **both** generated clients (admin and POS typings) are regenerated by the existing scripts, never by hand, and both apps' `api:check` pass.

### 2. Migration (`packages/db`)

One expand-only migration: `ALTER TABLE "user" ADD COLUMN nav_style text NULL` and a check constraint `nav_style IN ('A','B','C')` (a `NULL` passes). No backfill, no index, no grant (the table-level grant to `pospay_auth` in migration 0008 covers the column), nothing dropped. The Drizzle schema in `packages/db/schema/identity-auth.ts` gains the column with a one-line Arabic comment.

Adding a nullable column with no default is a catalog-only change. The migration runner (`packages/db/src/concurrent-migrations.ts`) runs one migration file in one transaction, so adding and validating in one file would hold the exclusive lock through the validating scan. Use **two migration files, two journal entries**: the first adds the column and the named check constraint `NOT VALID`; the second runs `VALIDATE CONSTRAINT`. Follow the house form of `0077` (file objects) and `0080` (employee import recovery) and say so in the notes. The Drizzle schema carries the column **and** the named check. The migration test proves: a user row that existed before the migration reads `NULL` after it; `pg_constraint.convalidated` is true after the second file; a direct `UPDATE … SET nav_style='D'` is refused.

**Migration lane.** Other migration PRs are ahead in the queue. Build and test with a temporary number on a private cluster (`lane.mjs`, one DB test run at a time). Do not run `pnpm db:generate` for the final number, do not open a PR. The final renumber, `db:generate` and the PR wait for the manager's «دورك».

### 3. Reader and writer (`packages/auth`, role `pospay_auth`)

Two exported functions (or one small facade) beside the existing personal-session code: read `nav_style` of one user by primary key; set `nav_style` of one user by primary key and return the stored value. They take the user id from the caller, never from request input, touch only the row `id = userId`, and are the only code that reads or writes the column. Follow how the package already reaches `user` on the auth connection (`packages/db/src/auth-database.ts`); do not export a raw client and do not open a new pool per request. A stored value outside the three (impossible with the check, defensive) reads as `null`. An unknown user id on write is a typed error from `packages/db` conventions (CLAUDE.md §5), which the API maps to `UNAUTHENTICATED`; never a plain `Error`.

Arabic JSDoc on any `ports/**` method and `domain/**` function (CLAUDE.md §3.1).

### 4. API (`apps/api`, module `identity`)

On `MeController`:

- `GET /v1/me/preferences`, `@Authenticated()`, `principal.userId` required (`FORBIDDEN` when absent, as `me/workspaces`). Reads through `queries/my-preferences.query.ts`, which calls the `packages/auth` reader through a port the module defines. Read-only, no `domain/` or `use-cases/` import.
- `PUT /v1/me/preferences`, `@Authenticated()`, same `userId` rule, body validated with the contract schema (`VALIDATION_FAILED` otherwise). A write use case `use-cases/set-my-preferences/` calls the writer port. Registered in `AUTHENTICATED_WRITES` as `PERSONAL` with `checkedIn` pointing at the place that binds the write to `principal.userId`. No `Idempotency-Key` (no money or stock effect), no `AuditLog` row (CLAUDE.md §8 exception), no outbox event, no `x-company-id`.
- Staff-purpose sessions stay refused before the controller (401) and a device token has no user (403): prove both with tests, do not add a second check.
- Neither route may accept a user id, a company id or any other selector from the request. The admin client attaches `x-company-id` from the selection cookie to every request: the two routes ignore it, and a test sends a stale and a forged header and gets the caller's own value.
- `GET` answers with `Cache-Control: private, no-store`.
- Reach the reader and writer through the single `AuthService`/closure the API process already builds in `main.ts` (narrow operations added to it); no new pool, no raw client.
- **Cross-site requests.** `@Authenticated()` passes through `AccessGuard` with no origin check, and Better Auth's origin check does not cover Nest routes. The protection for this write is what the other cookie-authenticated JSON writes have: a JSON `PUT` needs a browser preflight, and `shared/cors.ts` answers it only for trusted origins with credentials. Prove with tests: `OPTIONS` from the admin origin is allowed; `OPTIONS` from another origin is not; no `GET`, `POST` or form-encoded alias changes the value (a `POST` and a `PUT` with a non-JSON simple content type do not write). Do not claim the server refuses a direct `PUT` from an untrusted origin unless you add route-scoped enforcement; adding that is out of scope, report it as a note.

The read is one row by primary key; the «EXPLAIN» assertion for `queries/` files applies and asserts the primary-key index.

### 5. Admin: write on change (`apps/admin`)

- A small saver beside the style provider (not in `src/session/**`): one PUT in flight at a time per tab; a choice made while one is in flight replaces any waiting choice; when the flight ends the newest waiting choice is sent. So A then B quickly always ends with B on the account (FR-025, PREF-09 is the server half).
- `NavStyleProvider.setStyle` keeps doing what it does (state and cookie at once, no wait on the network) and hands the choice to the saver.
- When a save fails (refusal or network) the frame and the cookie keep the choice and a message with `role="alert"` says it was not saved to the account; it clears on the next successful save. New i18n keys in `ar` and `en`. Where the message is drawn: on the Appearance page under the style list, and as the app's existing notice pattern when the switch was made from the account menu (use what exists; no new `packages/ui` component).
- Calls go through the generated client and TanStack Query's mutation machinery or a plain function used by a hook; no `fetch` in a component.

### 6. Admin: read at sign-in (auth fence)

Both sign-in paths (`src/session/api/use-sign-in.ts` after a `done` outcome, `use-verify-totp.ts` after success) replace the single `clearNavStyleCookie()` call with one call to a new function that lives **outside** `src/session/**` (for example `src/shared/nav-style/apply-account-nav-style.ts`): it reads `GET /v1/me/preferences` uncached with a 2-second limit; a value writes the cookie; `null`, a refusal, a network failure, a malformed body or the limit clears the cookie. It never throws and never rejects. Only then `loadPage('/')` runs, as today.

The 2-second limit bounds the whole read, the fetch and the body decode together. The cookie is committed exactly once: an answer that arrives after the limit changes nothing (no late write that brings a value back). The read is made only after a completed sign-in: never on a TOTP challenge (`outcome === 'totp'`) and never after a failed attempt.

**The previous user's queued saves.** Today both hooks release `pending` before navigating, and `loadPage` announces the account change to other tabs only when it runs. With an awaited read in between, a save still queued or in flight for the previous account (this tab or another) could be sent under the new session's cookie. So:

- the submit stays pending (button disabled) until navigation starts, on both paths;
- the saver of section 5 belongs to one signed-in identity: on an identity change (sign-out, sign-in, the account-change broadcast that `shared/browser/load-page.ts` already sends, read how it works) it drops its waiting choice and never sends again for the old identity; the identity transition is announced **before** the account read is awaited, not after;
- test: a waiting save from account X is not sent after account Y signs in, in the same tab and through the broadcast.

**Auth fence:** inside `src/session/**` the only changes are: that one call and its import, keeping `pending` true until navigation, and the earlier announcement of the identity change if it has to be made from the hook. No change to `session-calls`, the gate, the forms, the redirects or anything else. More than this means stop and report.

Sign-out is unchanged: it still clears the cookie after a confirmed sign-out. The server layout is unchanged: it still reads the cookie only; the account value reaches it through the cookie written at sign-in.

The cookie writer must be importable from `src/shared` (today the writer is in `app/(dashboard)/_frame/nav-style/nav-style-cookie.ts` and `src/` may not import `app/`): move the write function beside `clearNavStyleCookie` and re-point the importer. No behaviour change in that move.

## Security notes for the implementer and the reviewer

1. The only identity the two routes use is `principal.userId` from the verified session. Grep the diff for any other source.
2. The write is a state-changing request authenticated by a cookie: it must be covered by the same origin/CSRF protection the other `@Authenticated()` writes get. Say where that protection is and prove the new route is under it.
3. The cookie remains a display hint. Nothing on the server trusts it beyond choosing a frame; a forged value outside the three reads as C.
4. The sign-in read must not delay or block sign-in beyond the limit, must not leak whether the account read failed, and must not run before the session is established.
5. No log line with the session, and none needed for the value.
