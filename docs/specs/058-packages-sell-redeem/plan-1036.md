# Plan 1036: map PackageRuleError to the public sale error catalogue

Issue #1036 (deferred from #1025, gate for 42-3b2). No migration: `orders_package_sales.error_code` is free text.

## Problem
`execute-package-sale.ts` stores `PackageRuleError.code` raw (`INVALID_COMPONENTS`, ...) as the refusal `error_code`.
Those names are not in the public catalogue (`packages/i18n` messages + `apps/api/src/shared/errors.ts`). Also,
`PackageSalePricingError('INVALID_LIMIT')` is stored raw (plan-42-3 says it is a programming error, not a refusal).

## Decision: reuse existing public codes, no new business wording
A sale re-runs `validatePackageDefinition`, slot creation and expiry on the STORED package type, so a rule error here
means the stored type is invalid. The public catalogue already has the matching `PACKAGE_TYPE_*` codes with ar/en text.

| PackageRuleError code | Public code | Reachable in a sale |
|---|---|---|
| INVALID_PRICE | PACKAGE_TYPE_PRICE_INVALID | yes |
| INVALID_COMPONENTS | PACKAGE_TYPE_INVALID_COMPONENTS | yes |
| DUPLICATE_SERVICE | PACKAGE_TYPE_DUPLICATE_SERVICE | yes |
| INVALID_SESSIONS | PACKAGE_TYPE_INVALID_SESSIONS | yes |
| INVALID_SLOTS | PACKAGE_TYPE_INVALID_SESSIONS | yes (slot creation from bad sessions) |
| INVALID_DATE | PACKAGE_TYPE_VALIDITY_INVALID | yes (expiry from bad validity_days) |
| INVALID_REMAINING_SESSIONS, PACKAGE_EXPIRED, PACKAGE_EXTENSION_NOT_LATER, PACKAGE_EXTENSION_TOO_LONG, INSUFFICIENT_SLOTS | none (`null`) | no (import draft, extension, refund, redeem only) |

`null` = broken invariant, not a named refusal: the worker treats it like any other unnamed error (existing
`PackageSaleRetryError` path, nothing persisted as a refusal). `INVALID_LIMIT` gets the same treatment.

## Worker-only vs HTTP split (second issue comment)
`PACKAGE_SALE_BRANCH_INACTIVE` sits in `PACKAGE_SALE_STATUS` (422) only because `STATUS satisfies Record<ErrorMessageCode, number>`
requires every i18n code. Recommendation: keep it there (the message must stay in i18n for the status screen) and record
the split in the contract as `packageSaleWorkerOnlyCodes = ['PACKAGE_SALE_BRANCH_INACTIVE']` (+3 lines) so 42-3b2 never
returns it as an HTTP status. A real type split touches `apps/api/src/shared/errors.ts` typing and is out of scope.

## Manager decisions (GO)
- Mapping approved. `null` and `INVALID_LIMIT` go to the retry path. On the final attempt `package-sale.processor.ts`
  already stores the generic code `PACKAGE_SALE_FAILED` (existing processor spec covers 3 unknown failures). This PR adds
  `PACKAGE_SALE_FAILED` to the contract enum (17 codes) and `packageSaleWorkerOnlyCodes`, and adds a processor/use-case
  test: a `null` PackageRuleError and an INVALID_LIMIT on the final attempt store `PACKAGE_SALE_FAILED`, never a raw code.
- `PACKAGE_SALE_FAILED` has no i18n message today; the contract spec lists it as the one code without a message
  (42-3b2 owns its wording). Not invented here.
- `packageSaleWorkerOnlyCodes = ['PACKAGE_SALE_BRANCH_INACTIVE', 'PACKAGE_SALE_FAILED']`.

## Handoff to 42-3b2
- `PACKAGE_SALE_FAILED` needs its ar/en message in `packages/i18n` (it is a worker-only generic terminal code with no
  message today); 42-3b2 owns the wording (manager decision on #1046).
- 42-3b2 must not return `packageSaleWorkerOnlyCodes` as HTTP statuses.
