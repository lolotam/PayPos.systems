## Design

### 1. Record shape (`package-sale-attempt.ts`)

```ts
export const PACKAGE_SALE_REPLAY_WINDOW_MS = 23 * 60 * 60 * 1000;
export type HeldAttempt = {
  key: string;
  scope: string;
  createdAt: number;
  seenAt?: number;          // highest device time at which this attempt was observed
  body?: SellPackageInput;  // absent only in the status-only record
  saleId?: string;
};
```

- `readSaleAttempt` accepts a record only when: `scope` matches; `key` is a non-empty string of at most 64
  characters; `createdAt` is finite; `seenAt` is absent or finite; `saleId` is absent or a non-empty string of at most
  64 characters; and `body` passes `sellPackageInput`, **or** `body` is absent and `saleId` is present. Anything else
  reads as `null` (unchanged fail-safe).
- `saveSaleAttempt(scope, attempt | null): boolean` returns `true` when the write or removal succeeded and `false`
  when storage threw. It still never throws.
- `updateOwnedSaleAttempt(scope, key, attempt | null): Promise<boolean>` resolves `false` only when the stored record
  is owned by `key` and the write failed; otherwise `true`.
- `statusOnlyAttempt(attempt, saleId): HeldAttempt` returns `{ key, scope, createdAt, saleId }` and nothing else
  (item 4). It is strictly smaller than the reservation it replaces, so replacing the stored value cannot exceed the
  quota the reservation already fitted in.
- `saleAttemptExpired(attempt, now): boolean` (item 1) is `true` when `now < attempt.createdAt` (the clock is before
  the attempt was created), or when `Math.max(now, attempt.seenAt ?? attempt.createdAt) - attempt.createdAt >=
  PACKAGE_SALE_REPLAY_WINDOW_MS`. It fails closed: a clock that moved backward can only block replay, never allow it.
- `saleAttemptExpiresIn(attempt, now): number` is the milliseconds until `saleAttemptExpired` turns true by the
  passage of time (`0` when already expired).
- `touchSaleAttempt(attempt, now): HeldAttempt` returns the same object when `now - (attempt.seenAt ??
  attempt.createdAt) < 60_000`, else a copy with `seenAt: now`. The one-minute step keeps storage writes rare.

These five helpers are pure and take `now` as an argument.

### 2. Per-scope held attempts (`use-sell-package.ts`, item 2)

- The hook keeps `useRef(new Map<string, HeldAttempt>())` keyed by `scopeKey`, and `useRef(new Set<string>())` of
  scope keys whose last journal write failed. A request that started under scope A reads and writes only the entry of
  scope A, whatever scope the hook shows when the request settles.
- `postSale` is split so each function stays under 60 lines:
  - `reserveSale(scopeKey, body, journal)` runs inside `withSaleAttemptLock`: `saved = readSaleAttempt(scopeKey) ??
    journal.held.get(scopeKey) ?? null`; `attempt = saved ? touchSaleAttempt(saved, Date.now()) : new attempt`;
    `journal.held.set(scopeKey, attempt)`; keep the existing `PACKAGE_SALE_RECOVERY_REQUIRED` throw; then
    `journal.onPersist(scopeKey, saveSaleAttempt(scopeKey, attempt))`.
  - `postSale` then returns `attempt.saleId` if known, throws `PACKAGE_SALE_VERIFICATION_REQUIRED` when
    `saleAttemptExpired(attempt, Date.now())`, and sends the request exactly as today.
  - On a first-request known refusal: `await updateOwnedSaleAttempt(scopeKey, attempt.key, null)`, then delete the map
    entry **only if** `journal.held.get(scopeKey)?.key === attempt.key`.
  - On acceptance: `settled = statusOnlyAttempt(attempt, saleId)`; set the map entry only if it still holds
    `attempt.key`; `journal.onPersist(scopeKey, await updateOwnedSaleAttempt(scopeKey, attempt.key, settled))`. The
    attempt object is never mutated.
- `journal.onPersist(scopeKey, ok)` adds or removes `scopeKey` in the unsaved set and triggers a re-render.
- Restore effect: on mount and scope change, `readSaleAttempt(scopeKey)`; when it returns a record, set the map
  entry, and when `touchSaleAttempt` produced a new object, persist it with `updateOwnedSaleAttempt`. When it returns
  `null`, leave any in-memory entry for that scope in place. On a `storage` event for this scope: set the entry when a
  record is read; delete it when `null` is read **unless** the scope is in the unsaved set (an in-memory attempt must
  survive another tab's event).
- Returned values: `recoveryRequired` and `verificationRequired` are computed from the entry of the current
  `scopeKey` with `saleAttemptExpired`; `journalUnsaved` is `true` when the scope is in the unsaved set and still has
  an entry; `releaseFailed` deletes only the current scope's entry (and its unsaved flag); `restoredSaleId` is
  unchanged in meaning.
- `discardExpired(): Promise<void>` (item 3): does nothing unless the current scope's entry exists, has no `saleId`,
  is expired and no request is pending. It then runs `updateOwnedSaleAttempt(scopeKey, entry.key, null)`
  (compare-and-delete under the scope lock, the #1077 pattern), deletes the map entry if it still holds that key,
  clears the unsaved flag, resets the mutation and re-renders.

  **Reading of «discard an expired attempt after manager verification»:** the operator ticks an explicit
  acknowledgement that she verified the original sale with the manager, and only then can discard. There is no server
  call and no new permission: the tier is Medium and the scope is the admin app. The server already refuses a
  duplicate only inside its idempotency window, which is why the acknowledgement text names the manager check.

### 3. Expiry with the screen open (`use-package-sale-window.ts`, item 5)

`usePackageSaleWindow(attempt: HeldAttempt | undefined)`: when the attempt exists, has no `saleId` and is not
expired, set a timeout for `Math.min(saleAttemptExpiresIn(attempt, Date.now()), 2 ** 31 - 1)` that bumps a local
state counter, and listen to `window` `focus` and `document` `visibilitychange` to bump the same counter (browsers
throttle timers in background tabs and while the device sleeps). The effect depends on the attempt's `key`,
`createdAt`, `seenAt`, `saleId` and the counter, so a capped timeout re-arms. `useSellPackage` calls it with the
current scope's entry.

### 4. Visible notices (`package-sale-recovery-notice.tsx`, items 3 and 6)

`PackageSaleRecoveryNotice({ mutation })` renders, in this order:

1. `packageSale.journalUnsaved` as `role="alert"` when `mutation.journalUnsaved`.
2. The existing `recoverOriginal` / `verificationRequired` alert when `mutation.recoveryRequired`.
3. When `mutation.verificationRequired`: a native checkbox labelled `packageSale.verifiedWithManager` and a
   `Button type="button" variant="outline"` labelled `packageSale.discardExpired`, disabled until the checkbox is
   ticked; clicking it calls `mutation.discardExpired()`.
4. The existing `mutation.isError` alert.

`package-sale-form.tsx` renders `<PackageSaleRecoveryNotice mutation={mutation} />` in place of
`packageSaleRecoveryMessage(locale, mutation)` and drops that helper and its now-unused imports.

## Tests

Every UI test asserts a visible outcome (PP-7.2).

`package-sale-recovery.spec.tsx` (item 7): wrap the suite in `describe.each(['ar', 'en'] as const)`, set
`state.locale` in a nested `beforeEach`, and replace every `t('en', …)` and the `/The quote changed/` matcher with
the locale's text (`failedPackageSale.error.message_ar` / `message_en`). The separate `it.each` for the expired
message collapses into the suite. In «keeps recovery working in memory when storage is unavailable» also assert that
`packageSale.journalUnsaved` is visible.

`package-sale-recovery-window.spec.tsx` (new, also `describe.each` over both locales):

1. Stored attempt whose `createdAt` is two hours in the future: after reload the verification message shows, the
   retry button is disabled, and no sale request is sent.
2. Stored attempt one hour old whose `seenAt` is 23 hours after `createdAt`: same visible outcome.
3. Attempt one minute before expiry: retry is enabled; after `Date.now` is moved two minutes ahead and `window`
   receives `focus`, the verification message shows and retry is disabled.
4. Expired attempt: the discard button is disabled until the acknowledgement is ticked; after the click the
   verification message is gone, the journal key is removed, the price field's fieldset is enabled, the button reads
   `packageSale.submit`, and no sale request was sent.
5. Accepted sale: the stored record has exactly the keys `key`, `scope`, `createdAt`, `saleId` (plus `seenAt` only
   if present) and no `body`; after reload the form polls status and sends no second sale request.
6. A record with a 65-character `saleId`, and a record with neither `body` nor `saleId`, are both ignored: the form
   opens unlocked.

`use-sell-package-scope.spec.tsx` (new, hook level):

1. Scope A's request is in flight, the hook re-renders with scope B whose journal holds an unresolved attempt, then
   A's request is refused with a 400: B still reports `recoveryRequired`, and B's stored record is untouched.
2. With fake timers, an attempt one second before expiry reports `verificationRequired === false`, and `true` after
   the timers advance past the expiry instant with no other input.

## Not in this PR

- Clearing the journal by attempt key from the status read (the other fix #1077's review offered). The status-only
  record is smaller than the reservation, so its write fits wherever the reservation fitted; if storage throws
  anyway the operator sees `journalUnsaved`, and a replay inside the window returns the same sale.
- A clock set back by less than the time already elapsed, on a device that never observed the attempt at the later
  time, is not detectable in the browser. The server's idempotency window remains the authority.
- B2 (stale quote) is the next PR, stacked on this branch because both edit `package-sale-form.tsx`.

## Review round 1 (session review, before the PR)

Three findings from the line-by-line review went back to the implementer and are part of this PR:

1. The manager acknowledgement is bound to one attempt: the notice stores the acknowledged attempt key and the hook
   exposes `attemptKey`, so a discard, a scope change or another tab's newer attempt starts unticked.
2. `releaseFailed` and `discardExpired` read the held entry when they run, not the entry captured at render.
3. The «could not be saved on this device» warning hides once the sale reached `completed`, and after acceptance the
   unsaved flag clears only when a device read still holds the attempt's key (a storage read that throws no longer
   counts as a successful save).
