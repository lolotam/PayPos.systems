# #1075 B2 — stale quote in the package sale picker (plan)

Tier: **Medium** (Waleed, 2026-11-19, «كله Medium»). Plan author: Claude Fable 5.2 (medium).
Source: issue #1075 (picker item), `docs/plans/2026-11-19-design-and-backlog-plan.md` Track B2.

UX only. The server already refuses a stale quote with `PACKAGE_SALE_QUOTE_STALE`. No migration, API, contract,
permission or i18n change.

**Stacked on B1** (`fix/1075-b1-recovery-journal`, PR #1094): both PRs edit `package-sale-form.tsx` around the submit
button. This PR's base is the B1 branch until B1 merges.

## Problem

`PackageSaleTypeField` shows «Confirm the refreshed package and prices» when the selected type's quote changed after a
refetch, but the form still holds the old revision in `type` and the submit button stays enabled. Pressing «Sell
package» sends the old revision and only then learns it is stale.

## Rule

While the selected package's quote differs from the freshly loaded one, a new sale cannot be submitted: the submit
button is disabled and the submit handler does nothing. Pressing the confirm button adopts the refreshed quote and
re-enables the submit. Recovery of an original sale is not affected: it replays the saved body and never reads the
picker.

## Design

No effect and no mirrored state: the staleness flag already exists as `quoteChanged` in `usePackageSaleTypeOptions`.
It only has to be visible to the form.

`selectType` is the existing inline handler of the form (`setType(selected)` and
`form.setValue('price_paid', selected.price, { shouldDirty: true })`), moved into the state hook unchanged.
`onReconfirm` stays `setType`: it does not replace a price the operator typed (existing behaviour, covered by an
existing test).

## Decision recorded: a selected type that disappears

When a refetch succeeds and the selected type is no longer in the loaded pages, `quoteChanged` stays `false` and the
form stays submittable; the server refuses with `PACKAGE_TYPE_NOT_SELLABLE`. This PR does not change that. The list
is paginated, so «not in the loaded pages» does not prove the type was withdrawn, and blocking on it would lock a
valid sale.

## Tests (`package-sale-stale-quote.spec.tsx`, `describe.each` over `ar` and `en`)

Every test asserts a visible outcome (PP-7.2).

1. After a refetch that returns a changed quote for the selected type: the confirm button is visible, the submit
   button is disabled, and submitting the form (button click and `fireEvent.submit` on the form) sends no sale
   request.
2. After pressing the confirm button: the confirm button is gone, the submit button is enabled, and the sale request
   carries the refreshed `expected_type_revision` and `expected_service_revisions`.
3. After a refetch that returns the identical quote: no confirm button, the submit button stays enabled.
4. An unresolved original sale (lost response): the «Retry original sale» button stays enabled; staleness does not
   apply to recovery.

Existing tests that must pass unchanged: `package-sale-form.spec.tsx` (in particular «explicitly accepts a refreshed
one-option quote without replacing the intentional price paid»), the three recovery specs, `package-sale-result`.
